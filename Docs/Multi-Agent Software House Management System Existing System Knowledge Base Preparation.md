# **Knowledge Base Preparation**

## **1\. Purpose**

The Knowledge Base will provide approved company information to BD, PM, TL, Developer, Designer, QA, DevOps, and Orchestrator Agents.

It should ensure that agents:

* Follow the company’s approved processes.  
* Use consistent technical and communication standards.  
* Generate documents in the correct format.  
* Do not invent pricing, commitments, policies, or technical rules.  
* Use the latest approved information.  
* Respect project, department, and confidentiality permissions.  
* Provide a traceable source for every important recommendation.

The Knowledge Base should be treated as a **controlled company repository**, not as an unrestricted collection of files.

* Requirements are implemented.

* Developer testing is complete.

* QA testing passes.  
* No blocking bugs remain.

* Required screens are designed.

# **4\. Approval Statuses**

Draft  
Under Review  
Changes Required  
Approved  
Rejected  
Superseded  
Expired  
Archived

## **Status Rules**

### **Draft**

* May be edited.  
* Cannot be used for autonomous agent decisions.  
* Visible only to authorized authors and reviewers.

### **Under Review**

* Awaiting human review.  
* Agents may not treat it as authoritative.

### **Changes Required**

* Reviewer has requested corrections.  
* Must return to the owner.

### **Approved**

* May be used by authorized agents.  
* Effective-date rules must be applied.

### **Rejected**

* Must not be used.  
* Rejection reason must be stored.

### **Superseded**

* A newer approved version exists.  
* Retained for audit only.

### **Expired**

* Review date has passed.  
* Agents should stop using it until renewed.

### **Archived**

* No longer active.  
* Retained for historical or compliance purposes.

# **5\. Versioning Rules**

Use semantic document versions:

Major.Minor

Examples:

1.0 – Initial approved version  
1.1 – Small clarification or formatting update  
1.2 – Additional approved guidance  
2.0 – Major process, policy, or authority change

## **Major-Version Changes**

A major version is required when:

* Approval authority changes.  
* A process changes significantly.  
* Pricing rules change.  
* Security rules change.  
* A workflow or escalation path changes.  
* New mandatory requirements are added.  
* Previous guidance is no longer valid.

## **Minor-Version Changes**

A minor version may be used for:

* Wording improvements.  
* Additional examples.  
* Clarifications.  
* Non-material formatting changes.  
* Additional explanatory notes.

Approved versions must never be overwritten.

# **10\. Agent Retrieval Rules**

Agents must follow this retrieval priority:

Approved Project-Specific Knowledge  
→ Approved Client-Specific Knowledge  
→ Approved Department Standards  
→ Approved Company-Wide Policies  
→ Approved General Examples

Project-specific approved requirements should take priority over generic templates or historical examples.

## **Mandatory Retrieval Rules**

1. Use only approved and effective knowledge.  
2. Use the latest approved version.  
3. Do not use rejected, expired, or superseded guidance.  
4. Respect project and department access.  
5. Show the source document and version when making important recommendations.  
6. Clearly identify missing information.  
7. Do not convert an example into a confirmed requirement.  
8. Do not use historical pricing as a current price.  
9. Do not use another client’s confidential information.  
10. Stop and request human review when authoritative sources conflict.

# **11\. Conflict Resolution Rules**

When two knowledge items conflict, apply this order:

Approved Legal or Security Policy  
→ Approved Client Contract  
→ Approved Project SRS  
→ Approved Change Request  
→ Approved Project Process  
→ Approved Department Standard  
→ Company-Wide Standard  
→ Template  
→ Historical Example

When two items have the same authority:

* Use the newest effective approved version.  
* Create a knowledge-conflict record.  
* Notify the responsible owner.  
* Pause affected automated actions when risk is significant.

# **16\. Knowledge Base Acceptance Criteria**

The Knowledge Base will be ready for agent use when:

* Every active knowledge item has an owner.  
* Every authoritative item has human approval.  
* Every item has a version and effective date.  
* Expired and superseded versions are excluded from normal retrieval.  
* Confidential documents have correct permissions.  
* Credentials and sensitive information have been removed.  
* Search returns the correct approved source.  
* Agents can show which source and version they used.  
* Project-specific information takes priority over general guidance.  
* Conflicting information creates a human-review request.  
* All knowledge usage is recorded in audit logs.  
* Administrators can update knowledge without deploying new code.  
* Modified knowledge is automatically re-indexed after approval.

The Knowledge Base should initially be created from existing company documents, but every document must be reviewed, classified, standardized, approved, and versioned before agents are permitted to use it as an authoritative source.
