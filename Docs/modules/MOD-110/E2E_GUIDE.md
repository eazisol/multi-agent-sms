## 2. What this module is

Authentication proves an actor’s identity and session assurance. The current development slice can create local opaque bearer sessions, raise assurance with a debug MFA challenge, require step-up, revoke sessions, issue invitation tokens, and register service identities.

In this company it means a local tester can create a session, prove MFA, and revoke it immediately. It does not mean Auth0 login or production MFA is live.

## 7. API, data, and automated tests

Prefix: `/api/v1/auth`

| Method | Path | Behavior |
|---|---|---|
| GET | `/provider` | Provider metadata; `jwks_enabled: false` |
| POST | `/sessions` | Creates session and returns opaque `sess_` token |
| GET | `/sessions/me` | Resolves bearer session |
| POST | `/sessions/{session_id}/revoke` | Requires assurance level ≥ 2 |
| POST | `/mfa/challenges` | Creates local challenge; may return debug code |
| POST | `/mfa/verify` | Verifies code and raises assurance |
| POST | `/step-up/assert` | Requires requested assurance |
| POST | `/invitations` | Returns one-time `invite_` token |
| POST | `/service-identities` | Returns one-time client secret |

The integration tests prove local provider metadata, session resolution, low-assurance revoke denial, MFA level 2, immediate revoke, step-up level 3, duplicate pending invitation rejection, and one-time service credential creation.

```bash
uv run pytest tests/unit/auth tests/integration/auth -q --tb=short
```

[VERIFICATION.md](VERIFICATION.md) records an earlier 43-test suite but explicitly says PostgreSQL Alembic apply was not run.

## 8. Test flows

### F-SETUP

1. Ensure `MASMS_AUTH_PROVIDER=local` in a development environment. **Expected UI:** provider route reports `local`, JWKS false. **Data:** no secret values logged. **Evidence:** redacted metadata.
2. Prepare synthetic organization and actor IDs.

### F-HAPPY

1. POST `/sessions` with display name, assurance `1`, and TTL. **Expected:** `201`, session plus `sess_` token.
2. Call `/sessions/me` with `Authorization: Bearer <token>`. **Expected:** matching session.
3. Start MFA with purpose `login`; verify the local debug code. **Expected:** assurance `2`.
4. Revoke using the bearer token. **Expected:** status `revoked`.
5. Call `/sessions/me` again. **Expected:** forbidden immediately. Evidence must redact token/code.

### F-VALIDATE

1. Use malformed/expired token, wrong MFA code, invalid TTL, or unknown session. **Expected:** validation/forbidden/not found; no assurance increase.
2. Create duplicate pending invitation email. **Expected:** `422` in current integration test.

### F-AUTHZ

1. Try revoke at assurance `1`. **Expected:** `403`.
2. Try step-up assertion requiring `3` from assurance `2`. **Expected:** `403`.
3. Header `X-Assurance-Level` is a local/test stub; production must derive assurance from a validated session/IdP.

### F-TENANT

1. Create session/invitation under organization A; use headers/session context for organization B.
2. **Expected:** no cross-organization resolution or mutation. Session principal should preserve its own organization.

### F-CONCUR

1. Submit two revoke requests for the same session. **Expected:** final state remains revoked; no reactivation.
2. Verify the same MFA challenge twice. **Expected:** challenge cannot be used to raise assurance repeatedly. Record actual response.
3. No `expected_version` field is exposed; classic optimistic concurrency is N/A.

### F-TRANS

1. Validate `active → revoked` and challenge `pending → verified/expired` behavior.
2. Attempt revoked → active or verified challenge reuse. **Expected:** invalid/forbidden; no reverse transition.

### F-GATE

1. Call step-up assert for `production_deploy` at level 2 requiring 3. **Expected:** denied.
2. Complete step-up MFA and retry. **Expected:** assertion succeeds locally.
3. This proves assurance only; it does not grant deployment approval. Authorized human review remains mandatory.

### F-TERM

1. Revoked sessions are terminal for bearer use.
2. Invitation acceptance/cancellation/expiry UI is **Planned**; do not invent a reopen path.
3. Service secrets are displayed once; loss requires a future rotation/reissue process, not retrieval of the stored hash.

### F-RECOVER

1. On wrong MFA code, keep assurance unchanged and permit only policy-approved retry behavior.
2. Auth0 mode must remain **Blocked/fail-closed** because JWKS is disabled; do not fall back to trusting unverified tokens.
3. Email delivery and invitation acceptance are **Planned**.

### F-CLEAN

1. Revoke test sessions.
2. Clear shell/browser variables containing tokens, debug codes, invitation tokens, and client secrets.
3. Retain only IDs, status, timestamps, and redacted evidence.

## 9. Security, privacy, and approvals

- Tokens, MFA codes, invite tokens, and service secrets must never enter Git, screenshots, prompts, logs, or audit payloads.
- Only token/secret hashes are persisted; plaintext is returned once.
- Debug MFA codes are acceptable only in local/test/development.
- Auth0 is deliberately fail-closed until tenant configuration and JWKS validation are approved.
- Step-up assurance complements, but never replaces, permission, scope, exact-version, and human approval checks.
